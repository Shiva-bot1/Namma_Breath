pytest Edge-Case Tests — generate_advice() & Exposure Score

File: backend/test_advisory.py · New class: TestEdgeCases

25 new tests were added to the existing suite, grouped into three families that directly address the most likely failure modes for a responsible-AI advisory system: clean zero-input behaviour, graceful fallback on invalid inputs, and correct clipping at extreme multiplier combinations.

Family A — AQI = 0
  • test_aqi_zero_exposure_score_is_zero — score is exactly 0.0 for worst-case transport/time combo
  • test_aqi_zero_generate_advice_returns_favorable — only "favorable" tip fires at score 0
  • test_aqi_zero_headline_is_low — headline is "low", never "moderate" or "high"
  • test_aqi_zero_no_need_n95_tip — need_n95 rule does not fire
  • test_aqi_zero_no_wear_mask_tip — wear_mask rule does not fire
  • test_aqi_zero_no_purifier_hydrate_tip — purifier_hydrate rule does not fire
Family B — mask="invalid_value"
  • test_invalid_mask_exposure_equals_no_mask — MASK_PROTECTION.get() falls back to 0.0
  • test_invalid_mask_exposure_score_same_as_none — numeric score identical to "none"
  • test_invalid_mask_wear_mask_tip_not_triggered — documents known design characteristic (see finding below)
  • test_invalid_mask_score_is_non_negative — score ≥ 0 always
  • test_invalid_mask_score_within_bounds — score ≤ 100 always
⚠ Design Characteristic Surfaced by Testing generate_advice() checks mask == "none" by exact string identity for the wear_mask tip, while the exposure score uses a dictionary lookup. An unrecognised mask (e.g. "invalid_value") gets 0.0 protection in the score — correct — but is treated as "something is worn" by the advisory rule, so wear_mask is silently suppressed. The test documents this divergence explicitly so any future contributor is not surprised. No fix is required for the demo scope; a production hardening would normalise unknown masks to "none" before passing to generate_advice().

Frontend Bundle Audit — Code-Splitting Recharts & Leaflet

Files: frontend/vite.config.js · frontend/src/App.jsx · frontend/src/components/CompareView.jsx

The production build was emitting a single JavaScript bundle exceeding 700 KB, triggering Vite's built-in size warning. Recharts (~350 KB) and Leaflet + react-leaflet (~165 KB) together accounted for roughly 74% of the bundle. Both libraries are only needed when a specific tab is first opened, making them ideal candidates for lazy loading.

Changes made

vite.config.js Added build.rollupOptions.output.manualChunks function splitting recharts → vendor-recharts chunk and leaflet / react-leaflet / @react-leaflet → vendor-leaflet chunk.
Note Vite 8 uses rolldown internally; rolldown requires manualChunks to be a function (not an object). Object form throws TypeError: manualChunks is not a function and was corrected during implementation.
App.jsx TrendChart and CompareView converted from static imports to React.lazy(). Both wrapped in <Suspense> with contextual fallback text that reuses the existing trend-chart-loading CSS class.
CompareView.jsx RouteMap (the direct leaflet consumer) also converted to React.lazy() so the leaflet chunk is not fetched until the Compare tab is opened for the first time.

Code Review — WAQI Geo-Distance Check in fetch_live_aqi()

File: backend/app.py · Function: fetch_live_aqi() · Lines 198–208

The fix previously applied uses a Euclidean distance in degree-space to verify that the station returned by the WAQI geo-lookup is actually near the requested Bengaluru coordinate before accepting it as live data. The full implementation was audited independently.

Code under review

station_geo = data["data"].get("city", {}).get("geo")
if station_geo and len(station_geo) == 2:
    station_lat, station_lng = station_geo
    delta_deg = ((station_lat - lat) ** 2 + (station_lng - lng) ** 2) ** 0.5
    approx_km = delta_deg * 111
    if approx_km > 60:
        return None

Audit findings

AspectVerdictNotes
Distance method ✓ Correct Euclidean on (Δlat² + Δlng²)^0.5 × 111 is appropriate. At Bengaluru's latitude (~12.9°N), cos(12.9°) ≈ 0.974, so the longitude scaling error is < 3% — well within the 60 km threshold, no cosine correction needed.
Guard condition ✓ Correct if station_geo and len(station_geo) == 2 safely skips the range check when WAQI returns no geo data, avoiding a crash.
Debug endpoint parity ✓ Consistent /api/debug/waqi/<id> (lines 443–450) replicates the identical formula. Both code paths stay in sync.
Alternative expression ℹ Suggestion The same check could be written as math.hypot(station_lat - lat, station_lng - lng) * 111 > 60, which is marginally more readable and avoids the manual squaring. No functional difference — a stylistic option only.
Silent pass-through on missing geo ⚠ Design note If WAQI returns "geo": [] or "geo": null, the guard condition is false and the distance check is skipped entirely — the response is accepted as live data without any location verification. This is unlikely in practice but could be hardened with an explicit else: return None if strict geographic scoping is required beyond the demo.
✓ Bob independently confirmed the same class of issue The geographic check correctly addresses a real failure mode: WAQI's geo:lat;lng endpoint returns the globally nearest monitoring station, which could be in another state or country if no local station is available. Without this guard the "live" label would be silently misleading. The fix is the right approach — a coordinate-distance check rather than a fragile text-match on station names (which don't reliably contain "Bengaluru" or "Karnataka").
⚠ One additional hardening opportunity When station_geo is absent or malformed (empty list, null, fewer than 2 elements), the current code silently accepts the WAQI response without any location check. For a production deployment this edge case is worth handling explicitly. Suggested fix: add an else branch after the if station_geo and len(station_geo) == 2 check that logs a warning and returns None, so data of unknown geographic origin is always treated as unverified rather than accepted by default.

Summary verdict

The geo-distance fix is correct, well-reasoned, and appropriately documented in code. The 60 km threshold is generous enough to cover all 8 Bengaluru station coordinates without ever rejecting a genuine local station, and tight enough to exclude monitoring stations in other Indian states. No changes to app.py are required for the current project scope.

Responsible AI Write-up Notes

  • Accuracy / data honesty: The WAQI geo-distance check ensures the "Live" data label is only shown when the returned monitoring station is genuinely within ~60 km of the requested Bengaluru corridor — Bob independently validated this approach and confirmed it is more robust than name-text matching.
  • Known limitation documented: The wear_mask tip uses an exact string identity check (mask == "none") rather than a protection-level threshold.
